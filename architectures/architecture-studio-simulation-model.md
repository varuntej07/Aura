# Aura Architecture Studio Simulation Model

This document defines how the dashboard interprets the typed scenario registry in
`app/data/simulations.ts`. The simulator is a deterministic, local teaching and
decision-support model. It is not a production trace viewer, provider benchmark,
or control plane.

The architecture registry in `app/data/architecture.ts` is the source for
component responsibilities, connection meanings, runtime boundaries, provider
order, configured limits, and evidence. The simulation registry supplies
authored examples that move through that architecture.

## Truth boundary

Every animated step, event, payload, identifier, delay, retry, failure, tool
result, and telemetry entry is created locally from static TypeScript data.
Simulation playback must never contact Firebase, Firestore, LiveKit, Cloud
Tasks, a model provider, MCP, production logs, analytics, or a user account.

The UI must distinguish these categories:

| Category                  | Meaning                                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Verified architecture     | A source-backed component, connection, constraint, or configured order recorded in `app/data/architecture.ts`.           |
| Deterministic simulation  | A local scenario illustrating a source-backed behavior or boundary. Sequence and payloads are authored, not observed.    |
| Conceptual model          | A useful visualization, such as the Guide control loop, whose labels are not literal production runtime states.          |
| Source-only behavior      | Code exists but is not wired into the production voice path.                                                             |
| Adjacent behavior         | Source-backed behavior exists elsewhere in the backend but is not part of the voice runtime.                             |
| Unknown external behavior | The repository does not establish the value or policy. The simulator must stop at that boundary instead of inventing it. |

Component and connection positions are fixed during playback. Provider failures
change visual state in place; they never rearrange the architecture. Animation
durations are presentation values and must not be shown as measured latency,
SLOs, or provider performance.

## Typed scenario model

The shared types are defined in `app/types.ts`.

A `SimulationScenario` is a named family, such as `voice-turn` or `tool-call`.
Each scenario contains one or more `SimulationVariant` objects. A variant has a
stable id, display title, summary, and ordered list of `SimulationStep` objects.

Each step contains:

| Field            | Semantics                                                                                                                   |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `id`             | Stable module-order id generated by the local registry. It identifies an authored step, not a production call.              |
| `componentId`    | Architecture component to focus and animate. It should resolve in `architectureComponents`.                                 |
| `connectionId`   | Optional architecture edge to animate while the step is active. It should resolve in `architectureConnections`.             |
| `label`          | Short human-readable state shown in the simulator and telemetry rail.                                                       |
| `event`          | Local event vocabulary used to build a telemetry object. It is not necessarily emitted by production.                       |
| `responsibility` | Explanation of what the highlighted component owns at this point.                                                           |
| `payload`        | Redacted, deterministic inspection data. Values are illustrative unless the architecture evidence explicitly verifies them. |
| `durationMs`     | Virtual presentation duration. The helper defaults to 650 ms.                                                               |
| `status`         | Authored terminal presentation status. The helper defaults to `success`.                                                    |

`SimulationStatus` also includes runtime-only `idle`, `queued`, and `active`
states. The current registry authors terminal statuses only:

| Status    | UI meaning                                                                                                 |
| --------- | ---------------------------------------------------------------------------------------------------------- |
| `idle`    | No run is active.                                                                                          |
| `queued`  | The step belongs to the selected run but has not started.                                                  |
| `active`  | The step is currently highlighted.                                                                         |
| `success` | The authored step completed its expected local path. This does not independently prove an external effect. |
| `warning` | Playback continued through a fallback, qualification, or degraded state.                                   |
| `failure` | The authored variant injected or exposed a failure.                                                        |
| `blocked` | A guard, privacy state, duplicate, or unsupported boundary stopped progress.                               |

When a step becomes active, the component and optional connection are
highlighted and its payload becomes inspectable. On completion, the runtime
state changes from `active` to the step's authored `status`. Future steps remain
`queued`.

## Telemetry projection

The telemetry rail is a projection of the active local run, not a second source
of truth. Each entered step can produce one `TelemetryEvent`:

- `sequence` follows variant step order.
- `atMs` uses cumulative virtual scenario time, not wall-clock time.
- `type` comes from `step.event`.
- `label`, `componentId`, `status`, and `payload` come from the authored step.
- The event id must be deterministic within a replay.

Changing playback speed must not change event order, virtual timestamps,
payloads, statuses, or ids. Pausing freezes advancement. Resuming continues the
same step without duplicating its telemetry event. Clearing the telemetry rail
only clears the view; it must not alter scenario state.

## Playback, speed, and reset contract

Playback is an ordered cursor over one selected variant.

1. Starting a run marks every step `queued`, then activates step zero.
2. Only one step is active at a time.
3. After its presentation delay, that step settles to its authored status and
   the next step activates.
4. Playback ends after the final step settles. A failure or blocked status does
   not implicitly abort later authored steps; the ordered variant decides what
   follows.
5. A replay of the same variant produces the same steps, payloads, virtual
   timestamps, and terminal statuses.

Speed is a presentation multiplier. The wall-clock delay for a step is derived
from `durationMs / speedMultiplier`. Speed cannot alter the scenario data or
stand in for measured runtime performance. If the UI changes speed during an
active step, it may rescale the remaining presentation delay, but it must retain
the same cursor and emit no duplicate event.

Pause and resume preserve the cursor, completed states, active payload, and
remaining delay. They do not synthesize architecture events.

Simulation reset must:

- cancel the active timer or animation using a run-generation guard so an old
  callback cannot advance a new run;
- stop playback and return the cursor to its pre-run position;
- clear active component and connection highlighting;
- restore all steps to their deterministic initial state;
- clear run-scoped telemetry and the selected event inspector;
- retain the selected scenario, selected variant, playback speed, architecture
  view, surface selection, and personal decision workspace.

Changing scenario or variant performs the same run cleanup before selecting the
new data. Workspace reset is a separate, confirmed action that affects
localStorage-backed personal decisions. It must not mutate the verified
architecture or simulation registries.

## Scenario catalog

### 1. Run voice turn

Scenario id: `voice-turn`

| Variant                  | Semantics                                                                                                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `voice-turn-normal`      | Local waveform, VAD, endpoint wait, transcript finalization, context assembly, model generation, speech output, recorder observation, and detached post-session work. |
| `voice-turn-interrupted` | A new user turn interrupts assistant speech. The recorder marks the interrupted assistant text as non-factual.                                                        |

The complete endpoint display vocabulary is:

`idle -> speech detected -> speaking -> waiting for completion -> end of turn -> interruption -> finalized`

These labels are dashboard vocabulary. They are not a literal production enum,
and an individual variant may animate only a subset. The normal variant reaches
`end of turn` and then represents finalization with `transcript.finalized`; the
interruption variant explicitly uses interruption and finalized labels.

The verified runtime uses Silero VAD plus semantic endpointing when available.
If semantic endpoint detector construction fails, it degrades to LiveKit
VAD-based endpoint behavior. Configured endpoint and interruption thresholds in
the architecture registry are configuration facts, not animation durations or
measured latency.

The post-session step represents detached in-process `asyncio` work. It is not a
Cloud Task and has no durable restart or retry guarantee if the worker exits.

### 2. Firestore context read

Scenario id: `context-read`

| Variant               | Semantics                                                                                                             |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `context-all-success` | Eight source objects settle independently with deterministic staggered animation durations.                           |
| `context-one-fails`   | Archive retrieval fails, contributes an explicit typed default, and does not stop other reads.                        |
| `context-one-timeout` | One graph read holds the shared gather to its ceiling, so all eight results are discarded and replaced with defaults. |
| `context-deadline`    | The complete gather misses its verified configured 1.5-second ceiling, so the full result is replaced with defaults.  |
| `context-defaults`    | A fresh-user context is represented by complete keys with explicit empty or null values.                              |

The eight source categories in the typed architecture are profile, memory,
prior session, archive, Aura profile, entitlement, free voice budget, and graph
context. Some failure variants show only the meaningful requests, not all eight
step objects, so they must not be presented as exhaustive production traces.

The `durationMs` values are local presentation data. Only the aggregate
1.5-second startup ceiling is recorded as a verified configuration fact. No
production document is read during playback.

### 3. Dispatch Cloud Task

Scenario id: `cloud-task`

| Variant          | Semantics                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| `task-success`   | Deterministic enqueue, ownership transfer, authenticated delivery, atomic claim, action, and acknowledgement. |
| `task-retry`     | An injected retryable delivery failure leaves the action unsuccessful, then a later local attempt succeeds.   |
| `task-duplicate` | The deterministic task name suppresses a duplicate enqueue and prevents a second delivery.                    |
| `task-exhausted` | Playback stops at the repository's unknown external retry-exhaustion boundary.                                |

This entire scenario is adjacent to voice. It is based on the Signal Engine
scoring path:

`signal content ingest -> Cloud Tasks enqueue -> OIDC delivery -> signal scoring handler`

It is not connected to a voice turn, MCP tool execution, action receipts, or
voice post-session processing. The architecture canvas should render it
adjacent and disconnected from the core voice route.

An enqueue acknowledgement means Cloud Tasks accepted delivery ownership. It
does not mean the downstream action ran or succeeded. `queued` is the
simulator's conceptual state after acknowledgement, not a separately observed
application state.

The source-backed adjacent handler returns HTTP 200 for completed and
already-complete outcomes, 409 for a live lease, and retryable non-2xx behavior
for raised failures. The `task-success` fixture uses the verified 200
acknowledgement and keeps the adjacent handler separate from voice action
receipts.

The repository does not define the queue's exact maximum attempts, backoff,
dead-letter destination, or exhausted-retry policy. The `task-retry` second
attempt and `task-exhausted` boundary are deterministic teaching examples.
Their attempt counts cannot be described as production policy.

### 4. Execute tool call

Scenario id: `tool-call`

| Variant                       | Semantics                                                                         |
| ----------------------------- | --------------------------------------------------------------------------------- |
| `tool-read-success`           | Illustrates proposal through result-informed speech for an all-surface read.      |
| `tool-write-success`          | Illustrates one eligible write and a structured result artifact.                  |
| `tool-invalid-arguments`      | Shallow required-field validation blocks transport.                               |
| `tool-unsupported-surface`    | Surface metadata blocks a Desktop-only screen capability on Keyboard.             |
| `tool-stale-frame`            | A frame-dependent Desktop capability is absent from the turn's exposed tool set.  |
| `tool-implementation-failure` | A structurally valid call reaches its implementation and returns a failure.       |
| `tool-false-success`          | Exposes the current risk of model success wording without a runtime receipt gate. |

#### Structural policy

The verified action gate uses surface, frame freshness, finalized-turn state,
registered tool name, JSON object shape, and shallow required fields. It does
not infer authorization from transcript semantics. Speculative or non-final
turns expose READ tools only.

The execution filter keeps any reads plus at most the first non-READ call per
generation. A read and one write can therefore remain together. The registry's
`safe_concurrently` field is currently not read and must not be presented as an
enforced concurrency guarantee.

#### Remote MCP and local Desktop branches

The architecture registry and surface comparison distinguish two execution
routes. Successful read and write fixtures exercise authenticated MCP. Desktop
fixtures exercise the local pre-execution capability and freshness gates; they
do not claim to be successful local-tool traces.

Authenticated remote MCP carries these eleven all-surface tools:

- `list_reminders`
- `set_reminder`
- `cancel_reminder`
- `get_upcoming_events`
- `create_calendar_event`
- `query_memory`
- `store_memory`
- `web_surf`
- `get_user_context`
- `report_feedback`
- `track_topic`

The worker mints a Firebase ID token, the MCP middleware verifies it and binds
the exact uid, and a request-local `ToolExecutor` runs the implementation. A
voice MCP request has no `client_message_id`, so generic ToolExecutor
idempotency is not active. Reminder writes have their own semantic dedup;
calendar writes do not have a generic equivalent.

These four Desktop tools execute locally inside `BuddyAgent` and do not cross
authenticated MCP:

- `save_screen_item`
- `draft_outbound_message`
- `present_visible_artifact`
- `set_guide_mode`

Only screen save and outbound draft require a fresh frame at exposure time.
Fresh for the generic screen store means no older than the configured 15
seconds. Artifact presentation and Guide control do not use that capability
freshness requirement.

The stale-frame variant accurately illustrates pre-execution exposure: a
frame-dependent tool is omitted when the current frame is too old. It is not a
universal implementation outcome. If the frame disappears between exposure and
local execution, screen save can fall back to a text-only save, while outbound
draft publishes a local `no_frame` failure.

#### Results, receipts, and speech

A tool proposal is never success. Remote implementation results may be
structured successes, validation errors, timeouts, exceptions, or soft states
such as calendar `{ configured: false }`.

Recorder receipts are post-execution artifacts for allowlisted write tools.
Their shape includes tool name, call id, success, timestamp, and a small
allowlisted result projection. They do not gate speech. The current parser is
permissive: `configured:false`, arbitrary strings, `None`, and a non-boolean
error field can classify as successful. Post-session persistence keeps only
receipts whose parsed `success` is exactly true. A receipt therefore proves
that the recorder classified a completed call, not that every external effect
occurred.

Selected remote writes attach a tool-owned `say` line only after their result,
but this is not universal. `store_memory` and silent `report_feedback` do not
return that spoken field. Prompt and skill-brief instructions tell the model not
to claim success before a result, but those instructions are guidance.

`spoken_action_guard.py` contains pure helper functions but no production voice
path imports or calls them. Consequently:

- `tool-false-success` is an audit visualization of an unverified-claim risk,
  not a verified runtime rejection;
- `provider-tool` must not imply that the source-only guard currently blocks
  false success;
- the architecture's `spoken-action-guard` component must retain its
  `source-only` status.

The authored examples preserve the verified branch differences:

- `tool-read-success` returns the read result without creating a WRITE receipt.
- `tool-write-success` uses `set_reminder`, its required `message` and
  `scheduled_at` fields, its write-side concurrency budget, a structured result,
  and a recorder receipt.
- Unsupported-surface and stale-frame variants use the registered
  `save_screen_item` name, the `screen-frames` component, and verified
  connection identifiers.

The UI still keeps every value inside a prominent `SIMULATION MODE` boundary.
Payload content and playback timing remain illustrative, not observed
production events or measurements.

### 5. Provider failure

Scenario id: `provider-failure`

All provider events are locally injected. The repository records configured
adapter order and degradation behavior, but it does not emit a discrete,
application-level `provider.fallback_activated` event for these chains.
Telemetry with that name is simulator vocabulary.

| Variant                | Verified order or boundary                                                                                   | Simulation behavior                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `provider-stt`         | Deepgram nova-3, then Deepgram nova-2                                                                        | Attempt one fails locally; the fallback becomes active in place.                                                                         |
| `provider-endpointing` | Multilingual semantic detector, then VAD-based endpoint behavior                                             | Semantic construction fails locally; non-semantic endpointing continues.                                                                 |
| `provider-llm`         | Optional configured OpenAI model, then Anthropic voice model, then Google cheap tier                         | The current primary depends on configuration. The simulation advances from attempt one to attempt two without asserting a provider name. |
| `provider-tts`         | Cartesia sonic-3, Deepgram aura-2-andromeda-en with markup stripping, Cartesia sonic-2 with markup stripping | Primary speech fails, unsupported inline markup is removed, and fallback speech continues.                                               |
| `provider-context`     | Independent source failure becomes a typed default                                                           | Prior-session data fails locally and startup continues.                                                                                  |
| `provider-tool`        | Structured implementation failure can inform an honest model response                                        | The displayed source-only speech guard is not current production enforcement.                                                            |
| `provider-cloud-task`  | Adjacent Cloud Tasks delivery retains external retry ownership on non-2xx                                    | One local delivery failure produces a conceptual retry-scheduled event.                                                                  |

Configured provider order is not observed provider truth, and animation
durations are not performance comparisons. The containing component remains in
place throughout fallback.

### 6. Guide Mode

Scenario id: `guide-mode`

| Variant                 | Semantics                                                                                                                                                                                     |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `guide-repair`          | Explicit request and arming lead to observation, two unsuccessful instruction attempts, a later non-empty user turn, user-driven replan, a completion candidate, and successful verification. |
| `guide-privacy-blocked` | Guide begins off and observation remains unavailable.                                                                                                                                         |
| `guide-stale-frame`     | Observation-dependent progress is rejected when frame evidence fails freshness; the scenario does not claim that every stale frame disarms the coordinator.                                   |

The dashboard's conceptual loop is:

`OBSERVE -> PLAN -> INSTRUCT -> ACT -> VERIFY -> REPAIR`

This loop explains responsibility, not a literal production stage enum:

- OBSERVE consumes an authorized fresh Desktop frame.
- PLAN chooses the next instruction.
- INSTRUCT publishes one user-executable instruction.
- ACT belongs to the user. Aura never clicks.
- VERIFY compares later observed state with expected evidence.
- REPAIR means a later user-driven replan after failed verification.

The verified durable runtime uses stages such as `CAPTURE`, `PLANNING`, and
`VERIFICATION`. `repairing` is a dashboard label. In the current implementation,
two instructions without evidence can place the task in `REPLANNING`; the
runtime then waits for a later non-empty user transcript before it plans again.
The repair scenario preserves that pause, includes the completion-candidate
gate, and does not depict autonomous clicking or immediate self-repair.

Guide frame authorization is stricter than generic Desktop frame freshness:
Guide authorization requires a frame no older than 3 configured seconds, and
pointer decisions use a 2-second configured limit. The generic screen store's
15-second freshness boundary must not be substituted for those Guide gates.

When Guide is off, the Guide simulator visually disables observation and
Guide-frame-dependent controls. This is a privacy-state visualization, not a
rewrite of the surface registry: Desktop save and draft exposure are separately
controlled by generic frame freshness. Native Desktop remains the arming
authority, and that native client is in a separate repository.

## Authoring and maintenance rules

When adding a scenario or variant:

1. Reuse component and connection ids from `app/data/architecture.ts`.
2. Verify every claimed responsibility and fallback against current source
   evidence before writing the step.
3. Use static payloads with synthetic ids and redacted auth values.
4. Treat `durationMs` as presentation timing only.
5. Mark a degraded continuation `warning`, an injected failure `failure`, and a
   policy or privacy stop `blocked`.
6. Label source-only, adjacent, conceptual, and unknown behavior explicitly.
7. Do not create a production-looking log line, provider metric, retry policy,
   or success guarantee that the repository does not establish.
8. Keep scenario playback pure. It may read the registries, but it must not
   mutate them or persist run data.
9. Test replay, pause/resume, speed changes, variant changes, and repeated reset
   with no duplicate timers or events.

The architecture registry remains authoritative when a simulation payload and
a verified source claim differ. Such a mismatch must be fixed in the scenario
data or called out as illustrative, never silently promoted to production
truth.
